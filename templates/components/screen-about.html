P.A.C.K. | Pairwise Analysis and Cleanup Kit

Coordinating e621 post relationship cleanup and metadata reconciliation.

What is P.A.C.K.?

P.A.C.K. is a tool created to help coordinate cleanup projects on e621. By grouping semantically similar posts together into manageable clusters, contributors can quickly review matches, merge tag differences, link parent/child variants, organize pool sequences, and flag exact duplicate uploads.

Since I thought it would be pretty unproductive and rude to just drop a huge file full of unsorted and unhandled potential duplicate posts that I had found on people, I created P.A.C.K., which not only provides you a huge pile of unsorted potential duplicates to sift through, but also a work reservation system, visual comparison tools, a tag and metadata transfer system, and integrated e621 API actions to make reviewing and updating posts smooth and reliable.

How did you find these?

The core process behind identifying similar posts is graph-based clustering on nearest neighbors found from vector searches on image embeddings. If all of those words make sense to you, you probably know how the next part's going to go.

1. Feature Extraction

Image embeddings were generated for millions of posts using a ViT model (SigLIP 2 Naflex) fine-tuned as a multi-label classifier (tagger model) on e621 (Hydra 3.5). Hydra 3.5 relies on thousands of manual tag correction rules and is architecturally optimized for global and local feature classification. Extracting features with Hydra 3.5 aligns the embedding space with meaningful concepts described by e621 tags. It took about 40 hours to compute the embeddings for everything on a single RTX 3090 (fortunately I only have to do this once, then only on new images). If that sounds absolutely fascinating to you (and it should be! Making UMAP projections of e621 is extremely fun!), you can find the pre-computed embeddings as a HuggingFace dataset (RedRocket/Hydra-Embeddings).

2. kNN Indexing

All image embeddings were centered, normalized, and indexed into a FAISS flat L2 index to search for the 64 nearest neighbors. What this part gives me is the top 64 most cosine-similar images for every post on e621 along with the cosine distances. This part I do have to repeat in full every time, but it only takes 2.5 hours, and the resulting kNN distances are enough to do almost all of the fun things you can do with the embeddings in under a minute. (I also have the precomputed kNN distances available in the above dataset.)

3. Distance Thresholding

From the kNN dataset, candidate posts below specific similarity thresholds (depending on what I'm looking for) are clustered into groups. This produces high-quality results that focus on the semantic content of images rather than raw pixel values. And it's very important to have semantic similarity through a neural network for this sort of thing, since all of the fixed function methods tend to just throw you results that are completely out of left field on occasion. Ironically, the neural network is the more stable and predictable one here. There's a good reason why this has been the prevailing standard in image processing for about a decade.

You keep using that word, "graph", what does that have to do with anything?

At a fundamental level, any pair of posts on e621 can only have one of three possible relationship states:

  • Duplicates: Identical or near-identical uploads where one post is strictly inferior and needs to be flagged for deletion.
  • Related (Variants): Distinct variations or related artworks that should either be grouped into a pool or linked via parent/child relationships. (Fun fact: e621 rules technically mandate that parent/child hierarchies must be single-level, meaning all children point directly to one root parent and no grandchildren are allowed. Almost nobody follows this rule, leaving tens or hundreds of thousands of posts needing corrections, which I don't plan to do. But P.A.C.K. is designed to at least not make the problem worse.)
  • Unrelated: Entirely distinct artworks that were caught in the same vector similarity net. Since our search is based on semantic similarity, these often aren't entirely useless, and are actually very likely to have similar content, which can make them still useful for tag transfer.

Here's the catch: vector clustering frequently produces groups with more than two posts. If we naively forced multi-post clusters into isolated pairwise checks, you'd be trapped doing an O(N²) explosion of redundant comparisons. And worse, you'd spend time re-tagging or editing posts that end up getting deleted as duplicates five seconds later.

To avoid that nightmare, we have to look at how post relationships behave across whole groups at once. As if breaking out linear algebra wasn't enough, this is where we have to break out graph theory to solve the problem of correctly organizing furry artwork.

Inside any cluster, a single group of posts can contain multiple independent, separate duplicate subgraphs and variant subgraphs running side-by-side. P.A.C.K. models these as graphs to exploit how these relationship classes propagate, and more importantly, where they don't:

1. Full Subgraph Connectivity & Transitive Propagation

Both duplicate subgraphs and variant subgraphs are fully connected components within their own boundaries. If A is a variant of B, and B is a variant of C, then A, B, and C are all variants. Furthermore, all posts in a variant graph are correctly considered variants to every post inside a connected duplicate graph.

2. Severing Variant Links via Duplicate Collapse

Duplicate relationships do not propagate outward to variants (a variant of post A is not a duplicate of post A's duplicate). When a duplicate graph is collapsed into a single canonical "kept" post, P.A.C.K. severs all individual variant links pointing to the inferior duplicate posts and re-routes them directly to the kept post. This instantly eliminates dozens of redundant variant checks, tagging steps, and pool moves across posts that are destined for deletion.

3. Disjoint Set Propagation (Unrelated Sets)

If a set of variants {A₁, A₂} is declared unrelated to another set {B₁, B₂}, marking a single cross-pair (A₁, B₁) as unrelated proves the two variant sets are disjoint, and marks all remaining cross-pairs as unrelated.

Modeling post relationships this way is what ultimately makes the resolution process drastically simpler for human reviewers. The underlying complexity wasn't created by P.A.C.K., it was already inherently present in e621's web of post data. Graph theory is just how we keep it under control.

Now, if you're looking at this project in its initial/beta release state, you might notice that we're only looking at exact, pixel-for-pixel duplicates right now. Yes, this is overkill for that, but I have been looking over the vector search results for quite some time before deciding to make this site, and I decided to just do things correctly the first time around so I don't have to do a full stack redesign when I want to move to inexact matches. You have not seen what I have seen!
